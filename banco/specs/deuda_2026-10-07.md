## Fix 1 — utils/embeddings.py: el prefijo se decide antes de cargar el modelo

**Problema** (`embed()`, líneas 33-38): el prefijo `query: `/`passage:` se
calcula leyendo la global `_nombre_modelo` ANTES de que `get_modelo()`
corra (se evalúa en la línea del `if`, la carga pasa en la línea del
`return`). En la PRIMERA llamada de un proceso `_nombre_modelo` es None →
prefijo vacío. Si el modelo cargado es el segundo candidato
(`intfloat/multilingual-e5-large`, la familia que EXIGE prefijos), esa
primera tanda de textos viaja sin prefijo y las siguientes con él: espacio
de embeddings inconsistente. Hoy no se manifiesta (MiniLM es el primer
candidato y no usa prefijo), pero es una mina si el candidato preferido
cambia o falla.

**Fix**: cargar el modelo PRIMERO y decidir el prefijo DESPUÉS, sobre el
nombre efectivamente cargado:

```python
def embed(textos, consulta=False):
    modelo = get_modelo()  # primero carga: setea _nombre_modelo
    # la familia e5 exige prefijos query:/passage:; paraphrase no los usa
    prefijo = ""
    if _nombre_modelo and "e5" in _nombre_modelo:
        prefijo = "query: " if consulta else "passage: "
    return [list(v) for v in modelo.embed([prefijo + t for t in textos])]
```

**Test** (append a `tests/test_smoke.py`): no requiere fastembed — probar
el ORDEN de decisiones con monkeypatch: setear `utils.embeddings._nombre_modelo = None`, monkeypatchear `get_modelo` para que devuelva un fake y deje `_nombre_modelo` en un nombre con "e5", llamar `embed(["hola"])` UNA vez, y afirmar que el fake recibió el texto CON el prefijo `passage: ` (la primera llamada de un proceso con e5 activo ya prefija correctamente). El fake puede ser un objeto con `embed(list) -> iter` que capture el input.

## Fix 3 — carga_trazas.py: criterios no-string revientan el INSERT

**Problema** (líneas 57 y 65): `criterios = campos.get("criteria")` se
inserta tal cual en el `INSERT`. Si el .jsonl trae `criteria` como lista o
dict (formato legítimo de task yaml), `sqlite3` lanza `InterfaceError: Error
binding parameter` y la carga entera muere a mitad de archivo. Lo mismo
aplica a `task` y `modulo` (hoy strings en la práctica, sin garantía).

**Fix**: helper de coerción y aplicarlo a los tres campos de texto:

```python
def _texto(v):
    """None/str pasan; cualquier otro tipo se serializa a JSON (criteria
    puede venir como lista/dict del task yaml y sqlite3 solo acepta str)."""
    if v is None or isinstance(v, str):
        return v
    return json.dumps(v, ensure_ascii=False)
```

y en el INSERT: `_texto(modulo), _texto(task), _texto(criterios)`.

**Test** (append a `tests/test_smoke.py`): escribir un .jsonl sintético en
`tmp_path` con UN registro válido cuyo `fields.criteria` sea una lista
(p. ej. `["a", "b"]`), correr `cargar()` contra una db en tmp_path, y
afirmar: no lanza, total == 1, y la fila quedó con el criteria serializado
como string JSON (`json.loads` de la celda devuelve la lista original).

## Fix 2 — minar_errores.py: `eventos.index(ev)` empareja mal duplicados

**Problema** (`destino_del_reintento`, línea 106): `eventos.index(ev)`
busca por IGUALDAD de dict. Dos eventos idénticos (mismo nodo/accion/seg/ts
— posible: ts redondeado a ms y errores en la misma ronda) resuelven AMBOS
al primero, y el reintento del segundo se busca desde la posición del
primero: emparejo incorrecto. Además es O(n²) acumulado.

**Fix** (elegir UNO, actualizando los tests existentes si cambia la firma):
- (a) `minar_sesion` itera con `enumerate` y pasa la POSICIÓN:
  `destino_del_reintento(eventos, idx)` — firma nueva, más limpia.
- (b) mantener la firma y buscar por IDENTIDAD:
  `idx = next(i for i, x in enumerate(eventos) if x is ev)`.

La semántica no cambia: dado el evento de error en la posición idx, el
PRÓXIMO evento de la misma tool en la sesión (ok o error), con su delta.

**Test** (en `tests/test_minar_errores.py`): repro del bug — una sesión con
DOS errores idénticos de la misma tool (mismos ts) cada uno seguido de su
propio ok posterior, y entre medias otra tool; afirmar que cada error
empareja con SU siguiente (deltas correctas), no ambos con el primero.
Con la implementación vieja este test falla (el segundo error empareja con
el ok del primero); ajustar/adaptar los tests existentes de la firma si
cambió.

## Fix 7 — modules/db.py: los chequeos escanean dentro de literales

**Problema** (líneas 77 y 81): `PROHIBIDOS.search(consulta)` y
`_RE_LIMIT.search(consulta)` corren sobre la consulta ENTERA, literales
incluidos. Dos consecuencias: (a) `SELECT * FROM trazas WHERE criterios =
'delete'` se rechaza como "solo SELECT" (falso positivo conservador);
(b) `... WHERE criterios = 'limit'` hace CREER que hay cláusula LIMIT y no
se aplica el forzado → filas sin techo.

**Fix**: helper que devuelve la consulta con los literales VACÍOS (misma
máquina de estados de `_sentencias`, que ya existe en el archivo y ya sabe
qué es un literal `'...'`/`"..."`), y usar esa versión para AMBOS chequeos:

```python
def _sin_literales(consulta):
    """La consulta con el contenido de los literales ('...' y "...")
    reemplazado por vacío: para escanear palabras clave del SQL sin
    falsear por texto de usuario. Misma noción de literal que _sentencias."""
    partes, actual, comilla = [], [], None
    for ch in consulta:
        if comilla:
            if ch == comilla:
                comilla = None
            continue  # el contenido del literal no se escanea
        if ch in ("'", '"'):
            comilla = ch
        elif ch == ";":
            partes.append(";")  # el troceado de sentencias no se falsea
        else:
            actual.append(ch)
    partes.append("".join(actual))
    return "".join(partes)
```

(y en `sql()`: `limpia = _sin_literales(consulta)`; los chequeos de
PROHIBIDOS y _RE_LIMIT sobre `limpia`; la consulta que se EJECUTA sigue
siendo la original, sin tocar).

**Tests** (append a `tests/test_smoke.py`, junto a los de sql existentes;
usar una db sqlite real en tmp_path vía `DB_PATH` monkeypatheado):
1. `SELECT * FROM trazas WHERE criterios = 'delete'` → NO devuelve el
   error "solo SELECT" (corre; puede devolver (sin resultados)).
2. `DELETE FROM trazas` sigue rechazado (ya falla el startswith, igual que
   hoy).
3. `SELECT * FROM trazas WHERE criterios = 'limit'` → ahora recibe el
   LIMIT forzado (verificable porque la consulta ejecutada no lanza —
   sqlite acepta `... 'limit' LIMIT 50`— y porque ANTES del fix el test
   correspondiente con '%'unlimited%' ya cubría la cláusula; basta afirmar
   que no lanza y devuelve, o inspeccionar con sqlite trace si es simple).
